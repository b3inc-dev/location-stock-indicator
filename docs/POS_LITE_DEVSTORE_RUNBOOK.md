## 2. 前の準備（1 回だけ・約 20 分）

### 2.1 PC の準備
1. Node は `>=20.19 <22` か `>=22.12`（`package.json` の `engines`）。`node -v` で見る。
2. Shopify CLI を**最新**にする（dev preview・`app dev clean` は新しい版の機能。古い版だと動きが違うことがある）:
   ```bash
   npm install -g @shopify/cli@latest
   shopify version
   ```
   出た版の番号を書き留める（結果の記録に書く）。
3. PostgreSQL をローカルで動かす（セッションの保存に使う。SQLite は使えない）。例（Docker）:
   ```bash
   docker run -d --name lsi-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
   ```
4. リポジトリで #76 のブランチにする:
   ```bash
   git fetch origin
   git switch claude/loc-pos-lite
   git pull
   git log -1 --oneline   # 41f2309 かそれより新しいこと
   npm ci
   ```
   `npm ci` で `@shopify/shopify-app-react-router` が 1.1 系（`package.json` の `~1.1.1`）になります（#80）。開発ストアのセッションは、はじめから期限付きのオフライントークンで保存される見込みです（**推測**: #80 のフラグが 1.1 系で読まれるため）。
5. `.env.example` を `.env` に写し、`DATABASE_URL` だけを入れる（`SHOPIFY_API_KEY` などは CLI が入れるので空でよい。**秘密の値をコミットしない**）。
   - **`.env` に `FORCE_PLAN_LITE=1` を入れない。** これはアプリの料金プランを Lite に固定する試し用の値で（`app/utils/shopPlan.server.js`）、入れると開発ストアでも Pro の機能が止まり、「店頭受取・配送は Pro プランで使えます」になって確かめられない。POS の「Lite」（Shopify の POS のプラン）とは別のもの。
   - **`.env` に `EXPIRING_TOKEN_MIGRATION` を入れない**（#80 の古いトークンを移すスイッチ。既定オフ。オンにするのは T さんの別の承認）。この確かめでは使わない。

### 2.2 保護された顧客データ（名前・住所・電話）の申請（開発ストアだけなら審査なし）
Shopify の文書:「you can access customer data in development after Step 6」「You don't need to submit for review.」

1. Dev Dashboard（Partner の画面）→ アプリ → **Location Stock**（公開用）→ 設定（Settings）→ **Access requests**。
2. **Protected customer data** の「Manage」→「Customer data」を選び、理由を書く（例: POS の配送で注文の配送先を書く）。
3. 項目ごとに **Name・Address・Phone** を選び、それぞれ理由を書いて「Apply reasons」。
4. データの守り方（Data protection details）を書いて「Save」。
   - 配布の方法（公開）を先に選んでいないと申請できない（文書の前提）。
   - App Store に出すときの審査は別。ここでは出さない。

### 2.3 ロケーションと商品（開発ストアの管理画面）
1. ロケーションを 2 つ: **店舗 A**（POS で売る店）と **倉庫 W**。商品ごとの確かめ用に **倉庫 W2** も。
2. 確かめに使う商品 X（と Y）の在庫を、A・W（・W2）の全部に登録する（例: A 10・W 10）。W に登録が無いと「出荷元へ移せませんでした」になる。
3. 使うのは合成のお客様・合成の住所だけ。

## 3. 公開用のアプリを #76 で動かす（毎回・約 5 分）

1. 公開用の設定を選び、開発ストアで動かす:
   ```bash
   npx shopify app config use shopify.app.public.toml
   npx shopify app dev --store bbbincbbb.myshopify.com
   ```
   （`npm run dev:public` でも同じ。店を聞かれたら bbbincbbb を選ぶ）
2. 「Ready, watching for changes in your app.」が出るまで待つ。この画面は閉じない。
3. 記録（ログ）はこの画面に出る（Render ではない）。住所・名前が出ていないことも見る。

### 3.0 初めて動かしたあとに 1 回だけ: 公開用の URL が変わっていないか
dev preview は開発ストアだけに効くはずですが（文書）、初めて動かしたあとに確かめます。
1. `git status` と `git diff shopify.app.public.toml` で、toml の `application_url`・`redirect_urls`・`app_proxy.url` が `https://location-stock-indicator.onrender.com` のままか見る。変わっていたら**コミットせず** `git checkout shopify.app.public.toml` で戻す。
2. Dev Dashboard → アプリ → Location Stock（公開用）→ **Versions** → 今リリースしている版（Active）を開き、App URL が `https://location-stock-indicator.onrender.com` のままか見る（トンネルの `…trycloudflare.com` になっていないこと）。
3. 推測: 変わっていたら、ほかの店の公開用のアプリがトンネルを向いてしまう。すぐに `Ctrl + C` → `npx shopify app dev clean --store bbbincbbb.myshopify.com` をして T さんに知らせる（版を出し直すかは T さんが決める）。

### 3.1 権限の承認のし直し
1. ターミナルに出た Preview URL か、開発ストアの管理画面 → アプリ → Location Stock を開く。
2. 「権限の更新」の画面が出たら、足した 4 つ（注文を読む・注文を書く・自店で管理する出荷指示を読む・書く。`read_orders`・`write_orders`・`read_merchant_managed_fulfillment_orders`・`write_merchant_managed_fulfillment_orders`）があることを見て **承認（Update / Install）**。
3. アプリのナビに「店頭受取・配送」が出ることを見る。開いて、上に「要確認の注文を読めませんでした（権限…）」が**出ない**ことを見る（出たら承認できていない）。
4. 親の画面に「設定」の要約が 4 行（店頭受取・持ち帰りと配送の履行・送料の行・店舗ごとの配送）、その下に「要確認の注文」（「拾い直す」のボタンつき）があることを見る。はじめの要約は次のとおり（全部オフ）:
   | 区分 | はじめの要約 |
   |---|---|
   | 店頭受取 | オフ（POS の受取待ちは見るだけ） |
   | 持ち帰りと配送の履行 | オフ（会計のあとは何もしない） |
   | 送料の行 | 税あり・売上に含める・ポイントの対象にしない |
   | 店舗ごとの配送 | 配送を受け付ける店舗はありません（◯ 店舗） |
   各行の「編集」で区分の画面が開き、「←」（店頭受取・配送へ戻る）で親に戻れることも見る。
5. 推測: 公開用のアプリをまだ入れていない店なら、ここでインストールの画面になる。同じく承認する。

### 3.2 POS の端末でタイルを出す（Shopify の文書の手順）
1. ターミナルで `p` を押す → Dev Console が開く。
2. 端末（iPad / iPhone）の POS アプリで、bbbincbbb の **店舗 A** にログインしておく。
3. Dev Console の **Mobile** のプレビューのリンク → QR コードを端末で読み、出たリンクから POS アプリを開く。
4. POS のホームに「店頭受取・配送」のタイルが出る（出なければ POS の設定 → スマートグリッドの編集でタイルを足す）。

### 3.3 `orders/paid` が PC に届くかの確かめ（推測を確かめる）
dev preview で `orders/paid` がトンネル（PC）に届くかは、Shopify の文書に書かれていません（**推測**）。5 章でスイッチをオンにしたあと、最初の配送のある会計のときに確かめます。
1. 会計のあと、3 章のターミナルに次のどちらかの行が出るか見る:
   - `[location-stock] pos-lite sale`（`phase: "done"` などの結果つき。注文の ID と結果だけで、住所・名前は出ない）
   - 出荷指示ができる前なら、待ちの行のあとに、送り直しで `[location-stock] pos-lite sale` が出る
2. 数分たっても出ないときは、`orders/paid` が PC に届いていない（または公開用の Render に届いている）。そのときは確かめを止め、T さんに知らせる。管理画面「要確認の注文」の「再処理」では同じ処理を手で動かせるが、`orders/paid` の確かめにはならない。

## 4. POS Lite の準備（店舗 A を Lite にする）

stock-transfer-pos の PR #106（`docs/POS_LITE_READINESS.md` 5.2）と同じ手順です（T さん 11/23 4:15 の決定: まず開発ストアでロケーションを POS Pro から外せるか試す）。

1. 管理画面 → 販売チャネル → Point of Sale → 設定 → **POS Pro Subscription**。
2. 店舗 A を選び「Cancel POS Pro」→「Confirm downgrade」。
3. 結果を書き留める:
   - **すぐ Lite になった** → 5 章へ（これで「Lite で動く」を確かめられる）。
   - **30 日の期間の終わりまで Pro のまま**、またはボタンが無い → 開発ストアでは Lite を試せない。5 章は Pro のまま行い、結果は「Pro で確認・Lite は未確認」と書く。Lite の確かめは、Ciara の 1 店で試す案を T さんが改めて決める（11/23 4:15）。
4. Lite になったかは、POS アプリで A にログインし、標準の店頭受取の一覧などが出ない・使えないことで見る（画面の出方は推測。見えたものを書く）。
5. 推測: 開発ストアに POS Pro の契約がもともと無い（＝はじめから Lite）こともある。そのときは 3 のどちらでもなく「はじめから Lite」と書く。

## 5. スイッチをオンにする（管理画面「店頭受取・配送」）

設定は 4 つの区分に分かれています（#79）。親の画面の要約の行の「編集」で区分の画面を開き、オン・オフを変えて、その画面の「保存」を押します。**保存するのはその区分の値だけ**で、ほかの区分の値は変わりません。

**オンにする前に**（全部オフのまま）:
1. 3.1 の 4 のとおり、要約が全部オフ・「要確認の注文」が空であることを見る。
2. POS のタイル →「受取待ち」が見るだけ（ボタンが出ない）、「配送の分け」が「オフです」になることを見る。**ここまで何も書かれていない。**

**オンにする**（T さん。上から順に）:
| 区分（編集の画面） | スイッチ・値 | 最初の値 |
|---|---|---|
| 店舗ごとの配送 | 店舗 A の行: 「配送を受け付ける」・既定の出荷元・送料 | 印を付ける・W・800 円 |
| 送料の行 | 送料に消費税をかける | 印あり（はじめから） |
| 送料の行 | 送料の行を売上に含める／送料の行をポイントの対象にする | はじめの値のまま（オン／オフ。どちらも推測で決めた仮の値。T さんが決める） |
| 店頭受取 | POS で準備完了・引渡し完了を記録する | **オン** |
| 店頭受取 | 引渡し完了のときにお客様へ知らせる | オフのまま |
| 持ち帰りと配送の履行 | 会計のあと、配送分を出荷元へ移し、持ち帰り分を履行する | **オン** |
| 持ち帰りと配送の履行 | 店頭で履行済みになった配送分を取り消して出荷元へ移す | **オフのまま**（#76 の手順 14〜18 で在庫の戻り方を見るときだけオン） |
| 持ち帰りと配送の履行 | 印の無いまま終わった注文を拾い直して「要確認の注文」に出す | オフのまま（6 章の #77 の手順 4 のときだけオン） |

あわせて見ること:
- 「店舗ごとの配送」で既定の出荷元を A（売る店そのもの）にすると、保存できず理由が出る（何も保存されない）。
- 1 つの区分を保存したあと親に戻り、**その区分の要約だけ**が変わり、ほかの区分の要約は前のままであること（例: 店頭受取をオンにしても「店舗ごとの配送」の行は変わらない）。
- 「持ち帰りと配送の履行」がオフのあいだ、「要確認の注文」の「再処理」は「「持ち帰りと配送の履行」がオフなので再処理できません。」で止まる。

## 6. 確かめる（#76 の本文の手順 5〜20）

#76 の本文「開発ストア（bbbincbbb）で確かめる手順」の 5〜20 をそのまま行います（店頭受取・持ち帰りと配送の 3 点の会計・後日の返品・止まる場合・取り消して移す道の在庫の戻り方）。ここでは、とくに見落としやすい所だけ書きます。

#76 の本文の読みかえ（本文は設定を分ける前に書かれたため）:
- 手順 1〜4 は、この手順書の 2〜5 章で行う（「3 つのスイッチ」は 5 章の表の区分のスイッチ）。
- 手順 16「スイッチをオンにして保存」は、「持ち帰りと配送の履行」の編集の画面で行う。
- 「Render の記録」は 3 章のターミナルと読みかえる。

- 会計の前に、カートの「**フルフィルメント済みにする**」を**オフ**にできるか（Lite でできるか）を必ず書き留める。できなければ、#76 の手順 14〜18（取り消して移す道）が本番の道になる。
- 手順 10: 送料の明細に `_lsi_fee` などの印が**注文まで届いているか**（3 回目の見直しの「気になること 3」。届かないと POS Receipt・Shop Point が送料の行を見分けられない）。
- 手順 10: 2 点が倉庫 W に未発送であること（見直しの「気になること 4」。最初から販売店舗の外に出荷指示が無いことの確かめ）。
- 記録（ログ）は 3 章のターミナルに出る（#76 の本文の「Render の記録」はこの画面と読みかえる）。`[location-stock] pos-lite sale` の行が出ない会計があれば、3.3 のとおり止める。
- #77 の本文の「開発ストアで確かめること」1〜4 も行う（#77 は #79 を通して #76 に入っている）:
  1. 「配送を確定」のあと、通信を切って印付けを失敗させる → つないでもう一度「配送を確定」→ カートの送料の行が 1 つで、会計した注文の明細に `_lsi_fee="1"` がある。
  2. カートに手で「送料」のカスタム売上を入れて「配送を確定」→ 止まる文が出て、カートが変わらない。
  3. 「拾い直す」（スイッチはオフ）→ 見つかった注文の一覧が出て、注文のタグ・メタフィールドが変わらない。`source_name:pos` で POS の注文が出るかもここで見る（作られてから 5 時間を過ぎた注文だけが出るので、前の日の会計で見る）。
  4. 「持ち帰りと配送の履行」の画面で拾い直しのスイッチをオン →「拾い直す」→「要確認の注文」に出て、「再処理」で進む。終わったらスイッチをオフに戻す。
- `customers/redact`（#80 の取り込みで変わった所）は、手で起こしにくいので開発ストアでは確かめなくてよい（試験 `planPosLiteRedact` で確かめ済み）。確かめるなら、ターミナルの記録に注文の中身（住所・名前）が出ないことだけを見る。

## 7. 終わったら（毎回）

1. スイッチを**全部オフ**に戻す（「店頭受取」「持ち帰りと配送の履行」の 2 つの区分の画面で、それぞれ「保存」）。親の画面の要約が 3.1 の 4 の表のとおりに戻ったことを見る。
2. ターミナルで `Ctrl + C`（`app dev` を止める）。
3. 開発ストアを今リリースしている版に戻す:
   ```bash
   npx shopify app dev clean --store bbbincbbb.myshopify.com
   ```
   Shopify の文書:「restores the app's active version to the selected development store.」 dev で足した拡張・設定が消えると、それに結びついたデータも消える（文書）。注文・注文のメタフィールドは Shopify の注文に残る（推測）。
4. **自社用の設定に戻す**（`config use` で選んだ toml は次に選び直すまで残るため。そのままだと、次の `npm run dev` や `shopify app deploy` が公開用のアプリに向く）:
   ```bash
   npx shopify app config use shopify.app.toml
   ```

   `git status` で toml・`.env` 以外に変わったファイルが無いことも見る（`.env` はコミットしない）。
